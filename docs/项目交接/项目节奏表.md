## 一、工作规则

### 1. 谁说了算

| 事情 | 谁定 |
| --- | --- |
| 剧情、对白、做不做某个功能 | 阿鱼（依据 `docs/红缘原稿/`，不许自己编） |
| 画面好不好、拿不准的图 | 阿鱼最后看；明显合格的由 Claude 预审后直接接 |
| 代码怎么写、能不能合、微信能不能跑 | Claude（规格以 `godot/ASSETS.md` 为准） |
| 上传、部署、改小游戏后台、提审、花钱 | 必须阿鱼点头，由阿鱼本人操作或授权 |

文档之间冲突时，以日期新的为准；和阿鱼最新的话冲突时，以阿鱼为准。

### 2. 分支和提交

1. 唯一主线 `hongyuan-launch`，只从它出包。
2. 一张卡一个短分支、一个 PR，base 一律是 `hongyuan-launch`。
3. Claude 审过才合，合完删短分支；出包报告第一行写提交号。
4. 推送前跑 `godot/hongyuan/tests/run_all.sh`，不能比主线多出新的失败。
5. 不提交密钥和账号信息；`_inbox` 里的 `.import` 不提交。

### 3. 交接方式

- 各工位互相听不见，**一切交接写进仓库**：看板、任务书、PR、回执。
- 每次开工：`git pull` → 读本组看板 → 做自己名下「待做」「退回」的卡 → 做完改成「待判」并写提交号 → `git push`。
- 卡片状态只有六种：待做 → 进行中 → 待判 → 通过，或者 待判 → 退回 → 进行中。
- 每张卡不超过半天的工作量。
- 阿鱼只跟两个窗口说话：Claude 这边的项目聊天，GPT 这边的 D1。需要阿鱼拍板的问题攒在看板「待阿鱼拍板」一节，**每轮只问一次**，写清选项和建议。

### 4. 验收

- **只分两档：可以 / 不可以。**
- 证据三样：可打开的包（网页链接或预览码）＋提交号、通关录屏或截图、bug 表。
- bug 分级：**P0** 卡死或丢档，**P1** 明显错误，**P2** 小问题。P0 必须当天处理。
- 做的人不判自己的东西：画图的不判自己的图，接图的不判自己接的图。
- 同一个问题试三次还不过，就降级处理（热点改按钮、动画改静图），写进看板，不许停工。
- **审美也要验**（阿鱼：不许交丑东西）：新图和现有同类素材原尺寸并排比，再放大 2 倍看。逐条看构图、配色、层次、精致度、一致性、整体感觉，任何一条不过就退回，不许以「能用」「先凑合」放行。

### 5. 节奏和额度

- 工位手上还有没被卡住的卡，就接着做，不停下来问「要不要继续」。只有三种情况能停：卡全做完了；真被卡住了（看板写明在等谁）；周额度只剩 20%。
- 周额度剩 20% 时全部停手：先保证推上去一个能玩的包，再提交、更新看板，报告做到哪、还差什么。
- 测试证据交到 PR 或回执后，及时清理本地截图、录屏和临时包。
