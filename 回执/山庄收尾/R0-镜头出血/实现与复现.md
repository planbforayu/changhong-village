## 策略与交图接口

`estate_camera.gd` 共用同一套计算：`z=max(viewport_width/540, viewport_width/art_width, viewport_height/art_height)`。两轴使用同一倍率。相机四条 limit 以及拖动中心的夹取都使用实际画面矩形，保持平滑跟随；换尺寸时刷新并重置相机平滑状态。没有修改场景坐标、物件、脚点、导航、碰撞、人物身份、玩法、存档或跨世界数据。

当前 `camera_art_rect` 留空，实际矩形仍是 `(0,0,W,H)`。**尚未画好的出血不计入有效画面。** 现有 1024 高画布在长屏临时等比放大，因此会少看一些左右内容；没有拉伸、镜像或添加纯色遮罩。

后续美术接入时：先把真实底图/出血层摆在世界坐标 `(-136,-136)`，确认四边有完整不透明绘制、没有切断；再把该画布实例的 `camera_art_rect` 设置为 `Rect2(-136,-136,W+272,H+272)`，调用 `_fit_zoom()`。该字段只影响相机，不扩张可走区，不更改 layout 的 `size` 或任何点位。未完成的图不能设置扩大后的矩形。本轮只提供接口和测试，没有擅自宣布出血美术完成。

## 最低出血计算

按任务书的 540 内容宽，四尺寸理想可见范围分别为：

| 手机 | 理想可见画布尺寸 | 本次渲染内部尺寸 |
|---|---|---|
| 360×640 | 540×960 | 540×960 |
| 390×844 | 540×1168.615385 | 540×1169 |
| 430×932 | 540×1170.418605 | 540×1170 |
| 360×840 | 540×1260 | 540×1260 |

截图由 Godot 原生 SubViewport 直接输出目标手机像素尺寸，没有后期缩放。内部尺寸按最近整数取整，390/430 两档与连续理论高度的差小于半个画布像素；连续比例几何另有 960～1260 每像素高度的检查。

每侧最低为可见宽的四分之一，即 135；1024 高画布在 9:21 时还缺总高度 236，居中至少上、下各 118，仍被 135 的更严格要求覆盖。为了统一 2×2 画布像素颗粒，**交图用上、右、下、左各 136**。这里是相对原画布四边向外新增的保守预算，不是声称已有图里已经画出了这些出血。

旧版大多数画布按可见高度 1024 缩放，因此本基线不应一概描述为“9:21 已露底”；旧版像素图在短屏又会取整到 1。真正的 236 高度缺口出现在固定 540 宽、倍率为 1 的目标方案。本次统一规则，在出血未接入之前保持画面矩形不越界。

## 复现

在此工作区执行：

```sh
python3 godot/tools/run_estate_camera_r0.py --godot /Applications/Godot.app/Contents/MacOS/Godot
```

需先完成 Godot 资源导入，截图需要本机原生显示。所有 PNG、引擎日志和完整 JSON 都在已忽略的 `scratch/r0`，不提交图片。脚本退出 0 为所测项通过，2 为存在真实未到达的目标，1 为相机/资源/脚本等错误。汇总 CSV 和结果说明另见同目录。

- `test_estate_camera_r0.gd`：15 个真实场景构造器，加宴会厅 55/v11；每块四尺寸，从本块出生点开始，依次走可走区四边极值和配置中的所有交互/出入口点。各段均调用现有 `go_to` 和固定 1/60 秒 `_process`，不写目标位置、不用 `reset_to` 代替步行。唯一的初始位置设定是宴会厅构造后的出生点；其他场景用现有 build 的出生逻辑。
- 记录每段起点、目标、实到点、步数、累计路程、最大单步、非法站位步数和剩余距离；门口按原交互半径判定，四边要求误差 ≤2。门的中心在碰撞物里时，不假称到达中心。
- 四边是**现有可走网格极值**，不是不可走的图像外缘。目标选择不按连通性偷偷换成较近处。失败截图停留在实际走到的位置，CSV 标明未到达。
- 每个终点截图前只让相机平滑稳定，不移动人物。相机实际可见矩形通过 Viewport 逆变换读取，不使用相机目标位置冒充实测。
- `test_estate_camera_bounds.gd`：同一 Camera2D 连续换尺寸、极端四角拖动，开启平滑，含负坐标的未来真实出血矩形和 55 桌大画布。
