## 二、要照抄的「村子还原法」（`godot/ayu_home/v4/`）

村子之所以能玩，是每块区域都走了同一条流水线，山庄照搬：

1. **定稿图先行**：每块区域先有一张阿鱼认可的底图（如 `assets/approved-floor1.png`），不边做边改画。
2. **一份数据生成全部几何和交互**：`tools/build_world.py` → 每区一个 `xxx.json`（墙、门、家具遮挡、交互点），`tools/bake_navigation.gd` → `xxx.nav`。不手改生成物。
3. **统一交互模式**：点地面走、走近出气泡再操作，键盘 WASD/E 同样能用；门用真实门槛判定，不靠冷却。
4. **还原核对**：`tools/check_restoration.py` 拿实际坐标对定稿图，列出偏差。
5. **测试 + 实拍**：连通（navigation）、所有操作（walk_actions）、过门（ground_doors）、实际渲染截图（capture_validation），JSON/日志为证。
6. **素材清单**：`tools/make_manifest.py` 记长度和 SHA-256，导出预设排除证据和工具。

山庄对应改造：`assets/layered/scene_luoman_*/layout.json`（现由 `tools/layout_court/make_*.py` 生成）就是「数据层」，保留这条生成链，只把灰盒换成定稿像素图并补交互、补测试。

## 三、团队与流程（阿鱼 11/07 定，照村子工作组）

### 工位（GPT 侧，都是 Claude 的外包团队）
| 工位 | 角色 | 做什么 | 不做什么 |
|---|---|---|---|
| V1 | 总指挥兼总策划（用最强模型） | 接 Claude 的任务书，写策划方案交 Claude 定；定了以后拆卡、派给 V2～V5，叫醒停下的工位，汇报 | 不判自己团队的验收 |
| V2 | 开发核心 | 工具链、数据生成、导航、存档、跨世界衔接等底层 | 不画图 |
| V3 | 开发执行 | 按卡接图、接交互、写测试 | 不改底层框架（找 V2） |
| V4 | 绘图师 | 画风样板、每块定稿底图和积木、人物 | 不写代码 |
| V5 | 回归测试 | 用户体验（手感、遮挡、玩不玩得懂）、代码逻辑、文案三块全面过；新图和村子/爱情篇章同类素材并排比 | 不测自己做的东西；可以退回任何工位 |

### 模型配置（各工位自己配好，在策划方案和看板里写明）
- V1 总策划、V2 开发核心（算法/底层）：用最好的模型。
- V3 开发执行、V4 绘图师、V5 回归测试：用够用的便宜模型；V5 遇到难判的再升级。
- 默认不开最高推理档、不拉满额度，省 token；哪一步需要升档，V1 在看板上写原因。
- 看板每个工位那一行加一列「模型」。

### 流程
1. 阿鱼 ⇄ Claude 商量要什么 → Claude 写/改本任务书。
2. V1 出**策划方案**（`回执/山庄收尾/V1-策划方案.md`）→ 提 PR → **Claude 审定**（可退回）。
3. 定了以后 V1 拆卡派工，各工位一卡一 PR（base `hongyuan-launch`）。
4. V5 先测，过了 V1 复看，再交 Claude 审，Claude 合并。画风相关的图另外要阿鱼点头。
5. 平台叫不醒别的工位时，V1 第一时间如实说，给最省事的替代办法，不许假装已派出。

## 四、阶段（每个阶段由 V1 的策划方案细化，Claude 定）

### P0 · 自查 + 重画策划方案（第一件事）
V1 先找出以前的山庄分支并说明能用什么；再组织 V3/V5 自查：对照第一节逐块核对 16 块画布（画面、能玩什么、卡在哪，每块一张 360×640 真实截图，放 `回执/山庄收尾/P0-证据/`）、本地有仓库没有的山庄文件清单、连通表。V1 给出**逐块「保留 / 局部修 / 重画」建议表**：每块一行，附当前截图、理由（画风是否和村子/爱情篇章一致、站位图是否半成品）、改动范围；表放 `回执/山庄收尾/P0-留改表.md`。V1 据此写策划方案：各工位用什么模型、画风统一思路、每块画什么、玩法补什么、谁做什么、顺序和预计 PR 数、风险。
**验收（Claude + 阿鱼）**：留改表 16 块全有截图和建议，**阿鱼和 Claude 逐块定完**才进 P1；旧山庄分支找到并说清用法；模型配置写明；16 块全覆盖；截图真实；分工到工位、顺序清楚；只含文档和截图。

### P1 · 画风样板（V4）
只在定为「重画」的块里挑 3 处各画一张样板，同时和要保留的山庄满意画面（如湖边）放一起比，和村子（`ayu_home/v4`）、红缘爱情篇章（`hongyuan/`）同类画面原尺寸 + 2 倍并排对比。
**验收**：V5 并排比过 → Claude 审 → **阿鱼点头**才往下画。

### P2 · 还原工具链（V2）
照村子：山庄版 `check_restoration.py`、`estate_navigation`（16 块连通）、`estate_doors`（所有出入口来回）、`estate_capture`（每块实拍）测试，先对现状跑基线。
**验收**：headless 出 PASS/FAIL 明细；不改玩法代码。

### P3 · 逐块重画并接入（V4 画 → V3 接 → V5 测）
只做留改表里定为「局部修/重画」的块，每 1～2 块一个 PR；「保留」的块不动画面，只补站位图和玩法。写进 `tools/layout_court/make_*.py` 生成，不手改生成物。
**验收**：无灰盒色块；遮挡前后、远近大小正确；P2 测试全过；和样板同一画风。

### P4 · 补玩法（V3，底层找 V2）
每块/每个房间都有独立玩法（照村子：进去就有自己的事可做），至少 1 个走近可点的小事，沿用现有系统（`scripts/games/`、`scripts/kitchen/`、金币条等），参考：喷泉许愿、小卖部买喜糖、儿童乐园滑梯、休息厅台球、西餐厨房接厨房玩法、花园/前后门拍照点。
**验收**：逐个点到的测试；金币、签到、收成跨「山庄↔村子」往返不丢；文案 V5 过一遍。

### P5 · 整庄回归与打包（V5 主测）
故事入口 → 终章「去婚礼现场」→ 走遍 16 块 → 去村子 → 回山庄 → 刷新继续；Web 零 JSON 报错；07 号宾客图补齐；PCK 大小和分包方案。
**验收**：Chrome 360×640 全流程截图 + 日志；`run_tests.sh` 原断言全过。
