# Web r4 IDBFS 保存异常 · 只读审查

没有修改 content_packs.gd、checkpoint.gd 或导出包。当前结论是：一次真实持久化失败已被浏览器记录，但错误对象被引擎日志丢掉了，现有证据不足以宣布是配额不足、内存不足或某个确定的竞态；更不能把 localStorage 续档成功当成所有资源已离线缓存成功。

## 证据

- `browser-r4/log.json` 第 39 个记录（从 0 计数）为 `Failed to save IDB file system: undefined`。之前已请求村子 13 个媒体块，后续姓名/形象及 `weddingLocation=parking` 仍在 localStorage 中。日志没有该错误的 name、errno、transaction.error 或路径。
- `content_packs.gd` 把 PCK 存在 `user://hongyuan-packs/<sha>.pck`，Web 返回体写 `.part`、验证长度/SHA、重命名、挂载后立刻 `force_fs_sync()`。村子媒体约173 MB，13块，每块均触发一次整个挂载集合的持久化扫描。
- `checkpoint.gd` 仍写 `user://hongyuan_save.json.tmp` 并重命名，另外在同步 localStorage 后调用 `force_fs_sync()`。这意味着资源缓存和剧情存档共用 IDBFS 生命周期；浏览器刷新时能优先读取 localStorage 的较新 revision，所以这次人物信息保留不能证明 IDBFS 成功。
- r4 引擎 `index.js` 中 `GodotFS.sync` 已有 `_syncing` 保护；同一时刻再调用会打印 `Already syncing!` 并返回已解决 Promise，**不会排入下一次重试**。因此不能简单声称“并发 force_fs_sync 导致两个事务同时开始”。
- 引擎错误日志只打印 `error.message`。本包中的 `FS.ErrnoError` 类只有 `name="ErrnoError"`、`errno`，没有 message；它确实可以产生 `undefined`。因此“undefined就是IndexedDB配额不足”不成立，缺失/重命名中的文件也应排查。
- IDBFS 的顺序为 `getLocalSet → 异步 getRemoteSet → reconcile → loadLocalEntry/storeRemoteEntry`；前后文件集合可能改变。这是值得验证的竞态路径，但当前日志没有路径和 errno，**尚未复现为本次根因**。

## 最小诊断改动（建议先做，仅开发导出）

在新的诊断导出副本中补完整错误记录，不改旧 r4：
1. GodotFS.sync 的失败回调记录 `name, message, errno, String(error), target.error?.name, target.error?.message`，记录开始/结束的序号和时间；保留原报错，不吞掉。
2. 为 IDBFS.loadLocalEntry/storeRemoteEntry 的失败路径记录正在处理的路径、字节长度和错误 name/errno。只记录游戏 user 数据文件名，不打印存档正文。
3. 浏览器分别在开始、村子下载完、切回婚礼、刷新之前记录 `navigator.storage.estimate()` 的 usage/quota 与 `navigator.storage.persisted()`；这些数值只是诊断，不自动请求用户授权、不清空任何数据。

复现路线：独立浏览器 profile、同一 r4 基线测试存档 → 姓名/形象 → 村子13块全部下完 → 村子欢迎信 → 婚礼 → 立即刷新。至少一轮让13块下载限速、让保存发生在持续下载期间；另一轮每次下载后停留数秒再切换。记录完整错误与身份状态。刷新后离线再进入同一个目的地，确认到底哪些 PCK 真正持久化。

可控制故障注入：在开发副本将 IDBFS.getRemoteSet 返回延迟200～500 ms，放大“扫描与读取文件之间”的窗口，再重复路线；如果拿到 `ErrnoError errno=44` 与已消失的 `.part/.tmp` 路径，才可确认文件集合竞态。故障注入结果必须和真实网络正常运行分开记录。

## 最小修复建议（主线程决定具体实施后再改）

- 优先加**串行且可再试的同步协调器**：忙时设置 dirty 标记，当前同步结束后再跑一轮；不把“已经正在同步”当成后续改动已落盘。按整个下载组完成触发，而不是13块分别强制触发；剧情继续以同步 localStorage 保底。需要明确拿到 Promise 的结果，不能仅调用无结果的 force_fs_sync 就宣布成功。
- 若诊断确认 `.part/.tmp` 竞态：将下载临时文件写到非持久化临时区；完成校验后才导入稳定哈希路径。剧情文件也需要稳定的同步快照，不能在扫描到临时文件后删它。**不要只删除错误日志或取消校验。**
- 若诊断确认配额/大事务：将可重下的 PCK 持久化移到独立 CacheStorage/资源缓存层，仅让小型剧情状态走 IDBFS；持久化失败时降级当前会话缓存、明确可重试，不能令整个故事卡死。此方案比同步协调器改动大，但能避免把173 MB资源和小存档绑在同一 IDBFS事务里。微信桥现有缓存是另一条路径，不应一起重写。
- 仅把 `cache_root` 改成临时目录会破坏离线缓存；仅移除 force_fs_sync 会掩盖失败而不是修复；这两种都不建议作为“已修复”。

验收至少包括：正常完整下载、前台与预取合并、真实断网重试、坏哈希拒收、刷新续档、关闭/重开浏览器后离线命中资源、存储不可用时玩法仍可继续；保留原有8项loader测试。当前只读审查没有新增任何“浏览器持久化已通过”的结论。
